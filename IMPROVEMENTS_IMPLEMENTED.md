# Algorithm Improvements: What Was Actually Implemented

Following the limitations analysis (`LIMITATIONS.md`) and the reality check
(`HDR_REALITY_CHECK.md`), this pass implements real, working upgrades for the
highest-impact fixable limitations. **Being direct about scope**: a few items in
`LIMITATIONS.md` — perfect ghost removal, perfect tone mapping, full homography
under arbitrary motion — are open research problems with no closed-form
solution; nobody has "solved" them, including the professional systems compared
in `HDR_REALITY_CHECK.md`. What follows are genuine algorithmic upgrades that
measurably reduce (not eliminate) three of the documented limitations, plus one
correctness bug caught and fixed during implementation.

---

## 1. Softmax-weighted blending replaces hard argmax (`SaturationFusion.kt`)

**Problem addressed**: LIMITATIONS.md #1 — per-pixel argmax can flip which
frame "wins" between neighboring pixels, producing a visible one-pixel seam at
saturation boundaries (e.g. a flower's edge against leaves).

**What changed**: Instead of picking the single highest-scoring frame's pixel,
every frame contributes to the output pixel with weight
`exp(score_f / T) / Σ exp(score_g / T)` (a softmax over the same saturation
scores already being computed). At low temperature (T=0.05 default) this
reproduces the old argmax result almost everywhere; near a genuine tie between
two frames it blends smoothly instead of snapping between them pixel-to-pixel.

**What this does NOT do**: It is still a single-resolution, per-pixel
operation — it does not blend across spatial scales (a true Laplacian-pyramid
blend would additionally smooth boundaries a human eye perceives as edges but
that don't line up with a hard frame-selection boundary). That's a
substantially larger change (multi-resolution decomposition + reconstruction
per channel) not attempted here.

**Cost**: Same asymptotic complexity — this was already computing every
frame's score at every pixel; the change replaces "keep track of the max" with
"keep track of all scores, blend at the end," which is a few extra
multiply-adds per pixel per frame, not a new pass over the data.

## 2. Ghost guard via exposure-normalized variance (`SaturationFusion.kt`)

**Problem addressed**: LIMITATIONS.md #10 — a moving subject shows up as
ghosting because per-pixel selection can source different frames' content at
the same (i,j) with no way to tell "this pixel legitimately looks different
because of the exposure step" from "this pixel looks different because a
different object is there now."

**What changed**: Each frame's luma is normalized by that frame's own mean
scene brightness before comparison. For a static pixel, an EV bracket scales
brightness roughly proportionally across the whole frame, so the *normalized*
value stays roughly constant across frames regardless of exposure step; a
pixel whose actual content changed breaks that proportionality and shows
elevated variance in the normalized values. Where the coefficient of variation
exceeds a threshold (25% default), the guard falls back to the temporal
median across frames instead of the softmax blend — median is the standard
cheap deghosting trick because it discards a minority of outlier (ghost)
frames rather than blending them in.

**A correctness bug caught mid-implementation**: the first version of this
guard compared *raw* luma variance across frames. That's wrong for this
codebase specifically, because bracket frames are deliberately captured at
different exposures — a perfectly static scene's raw brightness is *supposed*
to swing widely between the -2EV and +2EV frames. Raw-luma ghost detection
would have flagged nearly every pixel as a "ghost" and defaulted to median
everywhere, silently discarding the entire saturation-selection mechanism this
app exists to do. The fix (normalize by each frame's own mean before
comparing) was necessary for the guard to mean anything on bracketed input;
it's called out here because it's exactly the kind of bug that looks correct
in isolation and only breaks on this codebase's specific capture model.

**What this does NOT do**: It cannot identify *what* moved, cannot recover
correct color/detail for the moved region, and cannot distinguish "subject
moved" from "gamma nonlinearity stretched this pixel's brightness
disproportionately in an extreme EV spread" — both show up as elevated
variance. A subject that's large, slow-moving, or high-contrast against its
background will still partially ghost. True deghosting needs per-object
motion estimation (optical flow + segmentation) — a different, much larger
algorithm not attempted here.

## 3. Linear-light exposure simulation replaces flat multiply (`SyntheticExposure.kt`)

**Problem addressed**: LIMITATIONS.md #4 — burst-stacking mode's synthetic
exposures were generated by multiplying the *stored* sRGB-gamma-encoded pixel
values directly by a brightness scale factor. That's the wrong operation:
real exposure control (shutter/ISO/aperture) scales the *linear* light
hitting the sensor, before the sRGB gamma curve compresses shadows and
expands highlights for display. Multiplying the already-gamma-encoded value
applies that compression twice in effect, pushing midtones/highlights too far
relative to shadows — visibly flat/washed synthetic exposures that don't look
like what a genuinely longer or shorter real exposure would produce.

**What changed**: `adjustBrightness` now decodes each channel from sRGB to
linear light (`srgbDecode`, inverse of the standard OETF), scales *there*,
then re-encodes (`srgbEncode`, the same curve `RawDemosaic` already uses in
the encode direction). This reproduces the actual physical relationship
between exposure and brightness. A small 256-entry lookup table avoids
repeating the decode math per pixel.

**What this does NOT do**: It's still a global per-pixel scale, not a tone-
mapping operator — no local contrast adaptation, no highlight rolloff beyond
simple clamping. A proper Reinhard/Drago-style operator would look more
natural at extreme scale factors; not attempted here since the scale factors
in use (±15% per synthetic step) are modest enough that clamping rarely
triggers.

## 4. Small-angle rotation correction added to alignment (`ImageAligner.kt`)

**Problem addressed**: LIMITATIONS.md #2 — alignment was translation-only, so
any rotational component of handshake (the wrist naturally twists slightly
during a multi-second bracket, not just translates) was completely
unrepresented; no (dx, dy) shift can correct it, since a true rotation moves
different parts of the frame in different directions.

**What changed**: Before the existing translation search, a two-patch
shift-difference estimate runs on each frame: independently estimate the
local translation of a left-side patch and a right-side patch (each via the
same normalized cross-correlation machinery, restricted to a sub-region). For
a small rotation θ around the image center, a point offset by +r from center
moves tangentially by approximately +rθ, and a point at -r moves by
approximately -rθ (small-angle approximation) — so the *difference* between
the two patches' vertical shift, divided by the horizontal distance between
their centers, approximates θ. The frame is then rotated back by -θ (via
`Matrix`/`Canvas`) before the existing translation search and crop run as
before, now against the derotated frame.

**Why this is deliberately conservative**: this is a coarse, linear estimate
from exactly two data points, not a robust multi-point fit — it has no way to
distinguish genuine small rotation from correlated noise between the two
patches. Estimates below 0.15° are treated as noise and ignored (skip the
rotation step entirely rather than risk introducing an artifact correcting
nothing); estimates are clamped to at most 4° regardless of what the linear
extrapolation says, since a two-point estimate at large inferred angles is
more likely wrong than right. The patch correlation search itself can also
simply fail to find a good local match (repetitive texture, low contrast) and
return noise, which is why the conservative clamping matters here more than
in the main translation search.

**What this does NOT do**: This is *rotation only*, not full affine or
homography — no scale change (zoom creep) or perspective (off-axis tilt)
correction. It's a first-order approximation of one specific handshake
component, not a general 2D registration upgrade; a genuinely robust solution
needs feature-based correspondence (e.g. ORB keypoints + RANSAC) across many
points, which is a substantially larger undertaking than this two-patch
heuristic.

## 5. Per-frame dynamic black level (`RawDemosaic.kt`, `CameraBracketController.kt`)

**Problem addressed**: README's "remaining known simplifications" — black level was a
single static per-camera value (`SENSOR_BLACK_LEVEL_PATTERN`), not each frame's own
`SENSOR_DYNAMIC_BLACK_LEVEL`, so sensor drift (e.g. with temperature) across a multi-frame
bracket wasn't tracked.

**What changed**: `ColorPipeline.blackLevels` is now a per-CFA-channel `FloatArray`
(R/Geven/Godd/B can each drift by a different offset) instead of one shared `Int`.
`CameraBracketController.captureOne` now waits for each frame's own `TotalCaptureResult`
and calls `RawDemosaic.withDynamicBlackLevel` to substitute that frame's
`SENSOR_DYNAMIC_BLACK_LEVEL` in place of the static per-camera fallback, when the capture
reported one.

**What this does NOT do**: Still one offset per channel per frame, not a per-pixel
calibration map — some sensors have subtle spatial black-level variation (banding) that a
uniform per-channel offset can't correct.

**Cost**: `captureOne` now serializes the RAW decode behind that frame's own capture
result instead of firing the moment the image buffer arrives. In practice the result
callback and the image-available callback land within the same capture, so this is not a
meaningfully slower critical path — it removes a race rather than adding a real wait.

## 6. Lens-shading (vignetting) correction (`RawDemosaic.kt`, `CameraBracketController.kt`)

**Problem addressed**: README's "remaining known simplifications" — the RAW pipeline
didn't correct the sensor's own vignetting, unlike a JPEG where the ISP already applies it.

**What changed**: When the device reports `STATISTICS_INFO_AVAILABLE_LENS_SHADING_MAP_MODES`
supports `ON`, `captureOne` requests `STATISTICS_LENS_SHADING_MAP_MODE_ON` and reads back
`STATISTICS_LENS_SHADING_CORRECTION_MAP` from that frame's capture result.
`RawDemosaic.demosaic` bilinearly interpolates that grid (typically a few dozen cells per
axis) into a per-channel gain multiplied into each raw sample before white balance.
Precomputed once per raw pixel ahead of the main demosaic pass (not inline per sample call
site), since bilinear demosaic re-reads each raw pixel from several neighboring output
sites — inlining the shading lookup would have redone its own 4-point interpolation up to
~9x per raw pixel.

**What this does NOT do**: The shading grid is defined over the sensor's
*pre-correction* active array, which is typically a few pixels larger than the active
array this file already crops to; this treats the two as the same region, a small
approximation on top of the bilinear grid interpolation itself, not an exact per-pixel
calibration.

**Cost**: One extra `FloatArray(w*h)` pass per RAW frame (a handful of float ops and array
reads per pixel), done once regardless of how many downstream call sites read a given raw
pixel during demosaic.

## What remains genuinely unsolved (not attempted, and why)

These are called out explicitly rather than silently left as before, because
they are not "improvements we didn't get to" — they are open problems where
even unlimited engineering effort doesn't produce a universally correct
answer, as `HDR_REALITY_CHECK.md` argues from how professional systems handle
(or fail to handle) the same cases:

- **True deghosting** (segment the moving object, treat it separately, fill
  correctly): needs optical flow + segmentation, a different algorithm
  category from per-pixel fusion. The variance-based guard here is a
  mitigation, not a solution — professional systems with far more compute
  still visibly struggle with fast or large-area subject motion.
- **General 2D registration** (homography, handling both rotation and scale
  and perspective robustly under arbitrary motion): needs feature-based
  correspondence across many points, not a two-patch heuristic. Even
  feature-based methods fail under repetitive texture or low contrast.
- **Perfect tone mapping** (map arbitrary dynamic range to a display range
  with no loss of information that looks "correct" to every viewer): dynamic
  range compression is inherently lossy and "looks correct" is a subjective,
  scene-dependent, even viewer-dependent target — there is no ground truth to
  converge to, which is why Reinhard, Drago, and every ML tone-mapping model
  produce visibly different, debatable results on the same input.
